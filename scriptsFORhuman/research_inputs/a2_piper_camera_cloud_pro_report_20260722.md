# A2 四足底盘 + Piper 单臂开门 Vision Student Camera 方案调研

**审计基线：** `843795013329d9478634c6d87db9756210a311ba`  
**Pinned tree：** [Jam-Stark/DoorDog@8437950](https://github.com/Jam-Stark/DoorDog/tree/843795013329d9478634c6d87db9756210a311ba)  
**目标分支：** `codex/a2-v13-student-distillation-20260717_2103`  
**任务边界：** 支持 Student 模仿 `base_v13_A` 已经出现的中间行为：接近、对准 handle、Piper 闭合、持续双侧夹持并推动门。现有证据是 `0/16 goal`、`16/16 stage4`、`4/16 stage5`、terminal hinge p50 约 `1.276 rad`，不能表述成完整穿门策略。

## 结论

> **推荐方案：一台 Orbbec Gemini 335L，固定在 trunk 前上方、向机器人右侧偏置，Student 继续使用单路 RGB-only `384×216`。**
>
> - **活动 camera 数量：1**
> - **型号：Orbbec Gemini 335L**
> - **Policy modality：RGB-only；depth 只记录和验证，第一阶段不进入 policy**
> - **目标采集：1280×800@60 fps，时间戳后以 latest-frame 方式供 50 Hz policy 使用，预处理为 384×216**
> - **安装：`trunk` 子安装架，初始 optical-frame pose seed 为 `[0.320,-0.140,0.250] m`、RPY `[0,-6,-8]°`**
> - **双 camera 升级：增加 Gemini 305 wrist camera；仅在单 camera 硬性遮挡门限失败后启用**
> - **三 camera：当前不采用**

选择单 camera 作为首选并不是认为 wrist view 没有价值，而是因为当前分支已经冻结为 **`81D proprio + 单路 RGB -> 12D`**。单路方案不改变 action、81D proprio、视觉 tensor 数量、ResNet18 输入接口或 LSTM contract；双路方案则需要明确修改视觉 observation/model，且在 4096-env 训练配置下会显著增加渲染和激活内存。 

**最重要的前置条件：当前 quaternion 不能直接继续微调。** R14 中 `CameraData.pos_w` 与 `trunk + configured offset` 的位置误差为 `0.859750361 m`。准确 IsaacLab API 显示 `update_latest_camera_pose` 默认是 `false`，而当前 `TiledCameraCfg` 没有覆盖该值；因此这次误差很可能至少包含“CameraData 返回初始化 pose”的因素，但尚不能由此断言 rendered RGB 的相机 transform 也错误。必须先完成同一步、多来源 transform 数值闭合。

## 1.2 81D proprio 的固定内容

**SOURCE FACT：** Student 的 81D 输入由以下项组成：

- base angular velocity：3
- projected gravity：3
- A2+Piper joint position：20
- joint velocity：20
- previous effective actions：19
- Piper delta actions：6
- A2 base command：5
- raw A2 base command：5

它不包含 door pose、handle pose、stage、gripper-handle transform 或接触状态。所有外部门/handle 信息都必须从 RGB 与 LSTM temporal context 中恢复。

**DERIVED：** 单帧 `384×216×3` 为 `248,832` 个 uint8 值，恰好与现有 one-update runtime 记录的视觉维度一致。历史 one-update Student 使用的是已封存的 `base_v10_D` Teacher artifact；这件事只证明训练路径工作，不代表 camera 选型，也不能替代未来针对 `base_v13_A` 的 Teacher 切换和重新蒸馏。

## 1.3 Piper 与 camera 的几何冲突

**SOURCE FACT：** Piper 固定在 `trunk`：

```text
arm_j0:
  parent: trunk
  xyz: [0.145, 0.0, 0.154]
```

当前 camera optical origin 是 `[0.25,0,0.14]`。两者相差：

```text
Δ = [0.105, 0, -0.014] m
‖Δ‖ ≈ 0.1059 m
```

也就是说，当前 camera optical center 只比 Piper pedestal 向前约 `10.5 cm`，高度还低约 `1.4 cm`。这是 arm link 在 pregrasp、folding 和 handle push 阶段穿越主视线的高风险布局。

URDF 还在 trunk 前部记录了一个中心为 `[0.25,0,0.119]`、大小 `0.08×0.05×0.02 m` 的简化 collision box；当前 optical point 只比它的顶部高约 `11 mm`。**INFERENCE：** 该 box 可能代表现有头部传感器、灯或简化外壳，不能把 `[0.25,0,0.14]` 附近视作可直接容纳任意实体相机的空空间，必须用实机或 CAD 确认。

# 2. R14 transform 问题：准确 IsaacLab API 结论

## 2.1 API 事实

**SOURCE FACT：** 在准确的 IsaacLab pin `c22775241e28f465fe345fa1a482ad6d29d712b0` 中：

1. `CameraCfg.OffsetCfg.pos/rot` 是相对 parent frame 的 pose。
2. `convention="world"` 表示 camera frame 采用 `+X forward / +Z up` 轴定义；它不表示 position 是绝对 world position。
3. quaternion 顺序为 `wxyz`。
4. `update_latest_camera_pose` 默认 `False`；为 false 时，CameraData 返回初始化时 pose。  
   [camera_cfg.py@c227752](https://github.com/isaac-sim/IsaacLab/blob/c22775241e28f465fe345fa1a482ad6d29d712b0/source/isaaclab/isaaclab/sensors/camera/camera_cfg.py) 

**SOURCE FACT：** `TiledCamera` 只有在 `update_latest_camera_pose=True` 时才调用 `_update_poses()`；其 `XformPrimView` 创建路径没有普通 `Camera` 中的 `sync_usd_on_fabric_write=True`。  
[TiledCamera source@c227752](https://github.com/isaac-sim/IsaacLab/blob/c22775241e28f465fe345fa1a482ad6d29d712b0/source/isaaclab/isaaclab/sensors/camera/tiled_camera.py) 

**SOURCE FACT：** 非 tiled `Camera` 明确使用 `sync_usd_on_fabric_write=True`，源码注释说明否则 fast pose query 可能读取 stale position。  
[Camera source@c227752](https://github.com/isaac-sim/IsaacLab/blob/c22775241e28f465fe345fa1a482ad6d29d712b0/source/isaaclab/isaaclab/sensors/camera/camera.py) 

**SOURCE FACT：** 若同一路径已经有有效 prim，官方 `spawn_camera` 会抛出 `ValueError`，而不是静默覆盖。  
[spawn_camera@c227752](https://github.com/isaac-sim/IsaacLab/blob/c22775241e28f465fe345fa1a482ad6d29d712b0/source/isaaclab/isaaclab/sim/spawners/sensors/sensors.py) 

## 2.2 根因假设排序

| 优先级 | 假设 | 当前判断 |
|---:|---|---|
| 1 | `update_latest_camera_pose=false` 导致 `CameraData.pos_w` 是初始化 pose | **INFERENCE：最直接解释 metadata stale，但不能解释或否定 rendered RGB pose** |
| 2 | CameraData、trunk rigid-body state、USD/Xform 在不同 step/reset 时间点读取 | **INFERENCE：高可能，尤其 staged reset 后** |
| 3 | TiledCamera Fabric/USD pose query 未同步 | **INFERENCE：源码差异支持，尚未数值证实** |
| 4 | `/Robot/trunk` 的 Articulation body pose 与 USD authored/composed prim pose 不一致 | **UNKNOWN：必须同时读取 robot.data 和 XformPrimView** |
| 5 | 同名 authored `ego_camera` prim | **UNKNOWN，但精确同路径静默覆盖概率较低，因为 spawn 应报错** |
| 6 | 当前 quaternion 本身错误 | **UNKNOWN；在 transform chain 未闭合前不能从 R14 误差反推** |

## 2.3 必须先通过的 transform gate

**DERIVED：以下为 hard pass/fail 标准。**

在同一个 simulation step、同一个 env 上，同时记录：

1. `robot.data.body_pos_w/body_quat_w` 的 trunk pose；
2. `/World/envs/env_N/Robot/trunk` 的 `XformPrimView` pose；
3. camera USD local transform；
4. camera USD world transform；
5. `CameraData.pos_w/quat_w_world`，分别测试 `update_latest_camera_pose=false/true`；
6. rendered fiducial 在像素平面的位置；
7. physics step、render step、scene update step、frame counter 和 timestamp。

测试条件为 reset 后、静止、A2 gait、pitch/roll、全 Piper sweep、stage3/4 door swing，至少 `16 env × 1000 frame`。

| 项目 | Pass | Hard fail |
|---|---:|---:|
| composed parent→camera vs direct world camera position | median ≤2 mm；max ≤5 mm | max >5 mm |
| orientation error | median ≤0.25°；max ≤1° | max >1° |
| rendered fiducial projection | median ≤2 px；p95 ≤5 px | p95 >5 px |
| camera prim 数量 | 恰好等于 env 数 | 缺失、重复或非 Camera prim |
| reset 前后 local extrinsic | 数值完全不变 | staged reset 改写 extrinsic |
| frame alignment | 所有 pose 来自同一 step | 无法证明同一步 |

在此 gate 前，下面给出的 pose 都是 **pose-search seed**，不是可以直接粘贴到训练配置中的最终 quaternion。

1. **SOURCE FACT：** 单 body RGB 已经在 DoorMan 中证明可支持完整门交互，但不是 A2 几何上的充分证明。

# 4. A2 本体自带 camera 是否可直接使用

**SOURCE FACT：** Unitree A2 官方文档给出的本体 optical camera 最高为 `2568×1448@15 fps`，FoV 为 `D153° / H132° / V77°`。A2 还提供 USB 3.0、千兆以太网以及 12 V/24 V 电源接口，但具体交付配置可能不同。`01-about_a2.html`  
[Unitree A2 官方文档](https://support.unitree.com/home/zh/A2_SDK_Development_Guide/about_a2)

**DERIVED：** 15 fps 对 50 Hz policy 意味着平均每 `3.33` 个 control step 才有一帧新图像。在 handle close、unlatch 和 door swing 阶段，这比 30/60 fps 更容易形成 stale visual feedback。

**UNKNOWN：**

- 相机具体型号；
- RGB shutter 类型；
- raw stream 是否可在 PC1/PC2 低延迟访问；
- exposure control；
- timestamp/sync；
- glass-to-host latency；
- 视频是否经过硬件编码；
- distortion calibration；
- 实际相机相对 trunk 的 optical-frame pose。

因此，A2 自带 camera 适合作为：

- 第三方录像/诊断 view；
- 超宽 context view；
- 双 camera 方案的廉价第三路候选；

但在上述 UNKNOWN 项未测量前，不应作为 50 Hz Student 的主控制 camera。

- [OrbbecSDK v2](https://github.com/orbbec/OrbbecSDK_v2) ([GitHub](https://github.com/orbbec/OrbbecSDK_v2))
- [OrbbecSDK ROS2](https://github.com/orbbec/OrbbecSDK_ROS2) ([GitHub](https://github.com/orbbec/OrbbecSDK_ROS2))

**UNKNOWN：** 尚未找到 Orbbec 针对当前 Isaac Sim/IsaacLab 版本的一体化官方传感器插件。仿真侧应使用实机标定后的 pinhole/distortion、曝光、noise 和 latency 模型，而不是依赖品牌专用 Isaac extension。

## 5.2 为什么第一阶段不把 depth 输入 Student

1. **SOURCE FACT：** 当前 Student contract 是 RGB-only；DoorMan 的 D435i 也明确关闭 depth。`Xue 等 - 2025 - Opening the Sim-to-Real Door for Humanoid Pixel-to-Action Policy Transfer.pdf`
2. **DERIVED：** 启用 depth 至少增加一条 16-bit image transport，并要求网络、normalization 和 sim depth noise contract 改动。
3. **INFERENCE：** handle、金属门锁、黑色/反光材料、近场遮挡和多相机 IR emitter 都会增加 active stereo/ToF 的 sim-to-real gap。
4. **推荐做法：** depth 同步记录，用于标定、visibility ground truth、近场距离和失效分析；只有在严格 RGB-vs-RGBD ablation 中带来至少约 `10 percentage points` 的 stage4/stage5 改善且不违反 latency 门限时，才进入 policy。

# 6. 四种架构比较

| 架构 | 优点 | 主要风险 | Observation/model 代价 | 结论 |
|---|---|---|---|---|
| **单 trunk/head RGB 或 RGB-D** | 保留现有单图 contract；覆盖 approach、door、handle、door swing；线缆固定 | arm/pedestal/gripper 遮挡；近场手指像素较少 | **无结构改动**；仅改 intrinsics/extrinsics与capture pipeline | **推荐首选**，但必须用高位、右偏、global-shutter camera |
| **trunk overview + wrist close range** | stage1-3 抓取细节最好；视角互补；一个被挡时另一个仍可见 | wrist cable、质量、碰撞；双流同步；约2×视觉计算 | 需要双图 observation 或新的融合方法 | **首选升级路径**；单 camera visibility失败时启用 |
| **两个互补固定 onboard cameras** | 无腕部线缆；同步和维护比 wrist 简单；可绕开中央 arm | 都不能保证最终 finger-handle close-up；重量和USB增加 | 双流网络改动同上 | **第二备选**，适合 wrist mechanical gate失败 |
| **三 camera** | 最大冗余，可同时覆盖全局、handle和侧向 door swing | 训练/部署复杂、带宽、同步、显存、维护成本高 | 至少约3×视觉路径 | **当前不采用**；缺少必要性证据 |

## 推荐的决策顺序

1. 修复/验证 transform。
2. 在相同 `384×216` 单图 contract 下搜索一台 off-axis trunk camera。
3. 单 camera 若通过 visibility、latency 和 matched behavior gate，则停止增加 camera。
4. 只有单 camera 在 finger close/hold 阶段出现不可恢复遮挡时，增加 wrist Gemini 305。
5. 三 camera 仅在双 camera 仍无法覆盖 wide-open door swing，或任务扩展到完整自主导航/建图时考虑。

# 7. 推荐 camera 的初始安装参数

## 7.1 坐标约定

**SOURCE FACT：** A2 URDF 中左腿位于 `+Y`、右腿位于 `-Y`，因此以下假设：

- `+X`：前方
- `+Y`：机器人左侧
- `+Z`：上方
- `convention="world"`：camera optical frame `+X forward / +Z up`
- quaternion：`wxyz`
- RPY quaternion 按 `Rz(yaw) Ry(pitch) Rx(roll)` 生成

当前场景为 `right/out`，handle 位于机器人右侧，因此主 pose-search 区域优先采用负 Y 偏置。 

## 7.2 推荐单 camera

| 字段 | 值 |

| Camera | **Orbbec Gemini 335L** |

| RPY seed | **`[0,-6,-8]°`** |
| RPY radians | `[0,-0.104719755,-0.139626340]` |

| Depth | 记录但不进入 Student；约0.17-20 m，推荐0.25-6 m |

## 双流网络建议

现有 `81D` proprio 和 `12D` action 不变。视觉侧推荐：

```text
trunk RGB ─┐
           ├─ shared-weight ResNet18 → [128D,128D]
wrist RGB ─┘
                         ↓
               LayerNorm + gated MLP
                         ↓
                        128D
                         ↓
                 现有 2-layer LSTM
```

不推荐：

- 直接把两图拼成 6-channel 后只修改第一层卷积；
- 交替输入 trunk/wrist 而不给 view identity；
- 把两个 16:9 画面强行压缩到一个 `384×216` mosaic；
- 用 privileged stage 切换 camera。

这些做法分别会破坏 pretrained convolution statistics、制造非平稳 observation，或显著损失单视角像素密度。

# 9. 各 stage 覆盖与遮挡预测

| 阶段 | 推荐单 trunk view | 双 camera 时 wrist view | 主要失效模式 |
|---|---|---|---|
| Reset / approach | **主视角**：门框、门扇、handle、地面和 base heading | gripper通常远离目标，价值低 | 过宽FoV导致handle像素过少；pitch/roll造成运动模糊 |
| Staging | **主视角**：handle高度和横向误差 | 可提供 arm endpoint方向 | Piper上臂穿过视线；handle落入宽角边缘畸变区 |
| Pregrasp | 同时看 handle、gripper、door panel | **最有价值**：精细 gripper-handle关系 | 当前 centered camera易被arm_body2-5遮挡；off-axis需验证 |
| Finger close | 必须至少看到 handle 和两侧 finger inner edge | **主视角** | handle、finger与door panel相互遮挡；近场失焦 |
| Unlatch | 看 gripper、handle转角和panel运动 | 看局部闭合与滑移 | wrist相机可能被finger或handle完全封闭 |
| Sustained hold / push | 看 door panel、handle区域、arm和base姿态 | 看局部是否继续围绕handle | 门扇旋转可能遮住trunk；wrist失去全局door swing信息 |
| Wide-open | **主视角**：门边、门框、开口方向 | 保留局部接触 | trunk看不到被门板挡住的另一侧；A2 yaw变化 |
| Doorway traversal | 能提供门框和corridor context | 价值下降 | 当前 `v13_A` 未完成该能力；不作为camera成功声明 |

**INFERENCE：** 对当前 `v13_A` 中间行为，最关键的视觉交集是：

```text
handle + 两个 finger inner edge + 至少一段 door panel edge
```

而不是始终完整看到整扇门。单 trunk camera 能否保留这个交集，是决定是否需要 wrist camera 的核心验证指标。

# 10. 算力、显存和带宽

## 10.1 当前单路输入

**DERIVED：**

```text
384 × 216 × 3 = 248,832 bytes/frame（uint8）
```

| 帧率 | 单 camera 未压缩 RGB8 |
|---:|---:|
| 30 fps | 7.46 MB/s |
| 50 fps | 12.44 MB/s |
| 60 fps | 14.93 MB/s |

4096 env 的单个同步 batch：

| 表示 | 理论图像数据 |
|---|---:|
| uint8 | 0.949 GiB |
| float32 normalized | 3.797 GiB |
| 双 camera float32 | 7.594 GiB |

这些数字还不包括 tiled rendering buffer、ResNet activations、反向梯度和 temporal rollout storage。

**INFERENCE：** 在当前 4096-env 配置中直接复制第二路 `384×216` camera，训练 render/activation 成本很可能接近翻倍，并可能要求减少 env 数、分阶段渲染或使用更低的 per-view resolution。必须用实际 Isaac RTX profiler 验证，不能根据纯 tensor 大小预测最终吞吐。

## 10.2 实机 USB 带宽上界

未压缩 `1280×800@60 YUYV`：

```text
1280 × 800 × 2 bytes × 60 ≈ 122.88 MB/s / camera
```

再加 `1280×800@30` 的 16-bit depth：

```text
≈ 61.44 MB/s / camera
```

两台 RGB+depth 的理论未压缩总量约：

```text
2 × (122.88 + 61.44) = 368.64 MB/s
```

因此双 camera 时应：

- 尽量使用不同 USB host controller；
- 采用短、屏蔽、锁紧的 USB3 cable；
- depth 只按验证所需分辨率/帧率传输；
- MJPEG 只能在测得 decode latency、jitter 和 motion artifact 后采用；
- 不要仅根据机器上有多个 USB-C 插孔判断它们属于不同 host controller。

A2 官方页面记录部分 USB3 Type-C 端口有 `1 A` 或 `2 A` 限流，但具体 PC1/PC2 和用户实机 revision 仍需核验。`01-about_a2.html`

## 10.3 当前 simulator 渲染频率风险

`render_interval=1`、physics 200 Hz，且代码在存在 RTX sensor 时每 physics step 可能调用 `sim.render()`，随后 `scene.update()`。**DERIVED/INFERENCE：** 当前 camera 虽供 50 Hz policy 使用，仿真侧可能在 200 Hz 生成/更新渲染数据，造成不必要开销。应分别测量：

- camera capture/update rate；
- RTX render rate；
- policy observation sampling rate；
- high-level control rate。

不能把四者都默认视作 50 Hz。

# 11. Bracket、线缆和机械限制

## 11.1 Trunk Gemini 335L

**DERIVED 设计目标：**

- camera：约133 g；
- bracket、紧固件、防护和短线合计后尽量 `<250 g`；
- bracket 第一固有频率目标高于主要 gait 激励的数倍；
- 相机相对 trunk 的动态位移 `<1 mm`、旋转 `<0.5°`；
- 不使用柔软长臂或松散球头；
- 可使用薄阻尼垫抑制高频振动，但不能形成低频晃动。

安装位置不得：

- 占用 Piper pedestal sweep；
- 阻挡 A2 原有照明、LiDAR 或散热；
- 超出机器人宽度形成撞门框突出物；
- 让镜头保护片在主视场内产生反射。

## 11.2 Wrist Gemini 305

**DERIVED 设计目标：**

- camera+bracket+cable moving mass `<120 g`；
- cable 使用高柔 USB3，固定在 `arm_body5/6` 附近；
- 在 joint6 全范围和 gripper opening/closing 下保留 service loop；
- cable 不得进入两指夹持区域，也不得扫过 handle；
- connector 要有 strain relief 和机械锁；
- 验证 cable drag 对 `arm_j6`、gripper接触和Piper温度的影响。

**UNKNOWN：** 当前仓库没有实机 Piper revision、wrist额定 payload、末端允许附加惯量、线缆布线或 housing CAD，因此不能仅根据 URDF mesh 宣称 wrist mount 安全。

## 11.3 功耗和散热

Gemini 335L 与305的标称总功耗不高，但建议为两 camera、USB转换和启动峰值预留至少约 `11 W` 的稳定5 V预算以及30%余量。单 camera 时应直接使用经过确认的独立 USB3端口；双 camera 时不得把两个设备同时接在未经测量的无源 hub 上。

|---|---:|

| pregrasp/close 时 handle + 两个inner finger edge 同时可见 | ≥90% frames |
| stage2-4 至少保留 handle 的有效部分 | ≥90% frames |

## 12.4 Depth validation

Depth 只作验证时：

| Camera | 测试范围 | Hard pass |
|---|---|---|

| 指标 | 初始 hard pass |
|---|---:|
| stage4 entry | ≥14/16 |
| stage5 entry | ≥3/16 |
| terminal hinge p50 | ≥1.15 rad |
| positive-motion bilateral hold | ≥95% |
| over-force ratio | ≤1% |

# 13. Calibration、同步与 sim-to-real randomization

## 13.1 实机标定

1. **Intrinsics：** 每台 camera 单独标定，覆盖目标 exposure、resolution、crop、保护片和工作温度。
2. **Trunk extrinsic：** camera optical frame 到 `trunk`，使用 AprilGrid/棋盘与机器人 base姿态联合求解。
3. **Wrist hand-eye：** camera 到 `arm_body6_to_gripper`，覆盖多个 j1-j6 姿态，而不是只在rest pose标定。
4. **Repeatability：** 每次拆装、碰撞、运输或更换 bracket 后复验。
5. **Timestamp：** 保存 sensor timestamp、host receive time、policy consumption time，离线计算frame age和jitter。
6. **Exposure/WB：** policy deployment使用固定或受控范围，不允许自动曝光在靠近白门板时产生长时序亮度漂移。

## 13.2 同步策略

单 camera：

```text
camera hardware timestamp
→ host receive queue
→ latest complete frame
→ fixed preprocessing
→ 50 Hz policy
```

双 camera：

1. 优先使用经厂商确认可跨型号工作的 hardware trigger；
2. 若 335L+305 的 cross-model trigger未被正式支持，采用 nearest timestamp pairing；
3. 超过15 ms skew的pair丢弃或复用上一对；
4. 记录所有 skew，不能在数据集生成后假设同步。

**UNKNOWN：** Gemini 335L 与 Gemini 305 的跨型号硬件同步、触发电平和实际 skew 必须在购买/bring-up阶段确认；不能仅因两者都标注“trigger”就假设可直接连线。

## 13.3 Simulation randomization

建议把 nominal calibration 作为中心，不进行不受约束的大范围 camera随机化：

| 类别 | 建议范围 |
|---|---|
| Trunk extrinsic | xyz ±10 mm；RPY ±3° |
| Wrist extrinsic | xyz ±5 mm；RPY ±3° |
| Focal/FoV | ±5% |
| Principal point | ±2-3% image dimension |
| Residual distortion | 依据实机校正残差 |
| Frame latency | 0-40 ms |
| Drop/duplicate | 短 burst 20-100 ms |
| 双流 skew | 0-15 ms |
| Exposure | 1-8 ms等效 motion blur |
| Appearance | gamma、WB、亮度、shadow、specular metal/black handles |
| Occlusion | arm links、finger、cable、bracket、door panel部分遮挡 |
| View dropout | 双 camera 时随机drop单一路；禁止同时drop两路 |
| Depth | holes、quantization、range-dependent noise、IR干扰、反光失效 |

DoorMan 的结果表明 texture、lighting、camera intrinsic/extrinsic 和 motion blur randomization 对 RGB sim-to-real 非常重要；但它并不意味着可以用随机化掩盖错误的 nominal transform。`Xue 等 - 2025 - Opening the Sim-to-Real Door for Humanoid Pixel-to-Action Policy Transfer.pdf`

# 15. 哪些新证据会推翻当前推荐

以下任何一项都会改变决策：

1. **单 camera 胜出：** 当前或新 trunk camera 在所有 visibility门限上通过，并在多 seed中达到 `v13_A` 中间行为；此时不应增加wrist camera。
2. **单 camera 失败：** 最优 trunk pose仍有 stage2-4 完全遮挡超过100 ms，或 handle+双finger可见率低于90%；应升级 trunk+wrist。
3. **Wrist mechanical失败：** cable reset、碰撞、温升或末端惯量导致超过0.1%的控制/图像异常；改用两个固定 onboard cameras。
4. **Gemini bring-up失败：** 335L/305 无法稳定60 fps、ROS2 driver不稳定、同步或热管理失败；改用 D436 trunk + D405 wrist。
5. **A2自带camera验证成功：** 实测为global shutter、端到端frame age p95≤35 ms、可稳定≥30/60 fps raw access且标定可用；可重新评估使用原装camera，减少额外硬件。
6. **Depth显著有效：** RGB-D相对RGB带来≥10个百分点的stage4/stage5提升，且没有增加不可接受latency/IR failure；届时可改变policy modality。
7. **两个固定camera等效：** 固定左右camera能达到与wrist相同的finger/handle visibility，同时显著降低线缆和机械风险；应选双固定。
8. **Rendered RGB transform也错误：** 若 fiducial projection证明当前rendered camera与配置不一致，所有pose比较作废，先修transform。
9. **任务扩展：** 若目标从`v13_A`中间行为升级为完整穿门、反向门、左右手性、复杂导航和建图，单 camera推荐需要重新审计。
